# RidgeArc — 製品構想・目的定義

初版：2026-11-25  
状態：構想整理版（実装仕様・優先順位・公開範囲は未確定）  
基準プロトタイプ：v0.10  
更新：2026-11-27（第6回UI/UX仕様・地図探索要件追加）

## 1. 製品の目的

地形・天体・光・気象から未来の風景を予測し、その風景に出会うための場所と時間を発見する。

RidgeArcは、撮影者が「この日に何が撮れるか」を知るだけでなく、「この風景を撮るには、いつ、どこへ行けばよいか」を調べられる撮影計画ツールを目指す。

提供したい体験は、計算結果を得ることだけではない。まだ見ぬ風景を発見し、実際に撮影へ出かけたくなることを重視する。

## 2. 当初および現在の主要目的

以下の5項目は、利用者（開発者本人）が明示した目的を整理したもの。番号は優先順位を意味しない。

| ID | 目的 | 入力の例 | 出力・達成したいこと |
|---|---|---|---|
| G1 | 太陽が山に隠れる時刻を知る（当初の目的） | 観測地点・日付 | 太陽の出現、部分遮蔽、完全遮蔽、再出現の時刻 |
| G2 | 太陽の軌跡と指定地点から見える山の稜線を視覚的に把握する | 観測地点・日付・時刻・視点高 | 同じ角度座標系で描く地形と太陽円盤・軌跡。地形の重なり、全方位の閲覧、画角調整 |
| G3 | 指定地点で太陽が望んだ位置・軌跡になる日時を知る | 観測地点・希望する構図・探索期間 | 条件を満たす日付・時刻の候補（ダイヤモンド富士など） |
| G4 | 山に囲まれた地域でも、地平線まで太陽が沈むのを見届けられる地点を探す | 探索地域・日付または期間 | 可視条件を満たす候補地点。該当地点が存在しない場合と、データ不足で判断できない場合も区別する |
| G5 | 指定した被写体地点から太陽が昇る、または沈むように見える観測地点と日時を逆算する | 被写体地点・標高・日付または期間・出現／沈降条件 | 地図上の候補曲線、対応する日時。実際に行けるかどうかは当初は利用者が地図から判断する |

G5の「指定した場所」は、ここでは撮影者の位置ではなく、太陽が重なる山頂・地形等の被写体地点と解釈する。厳密な一致曲線に加えて太陽の視直径や許容構図差を反映した帯を表示する案がある。距離、標高、地球曲率、途中の地形遮蔽によって解が変わるため、単純な方位の延長線だけで判定しない。曲線・帯の具体的な定義は設計段階で決める。

G4の「地平線」は、山による遮蔽のない遠方の地平線・水平線を意図する。見かけの地平線、地球曲率、大気差、太陽円盤のどの部分まで見届けるかという成立条件は未定義。

## 3. 拡張目的（製品全体の要件、初期公開範囲は未定）

### 3.1 月と夜間の天体

- 月の位置、軌跡、月相、視直径、出現・遮蔽を扱う。
- 月と地形の重なりから、パール富士等の撮影条件を探索する。
- 太陽の機能と共通の観測地点・日時・構図を使う。

- 天の川・星空を地形と重ね、位置・見え方・撮影日時や観測地点の探索に利用する。
- 光害の分布を表示し、星空撮影条件の評価に利用する。

月・天の川・星空・光害への対応はv0.10では未実装。

### 3.2 光・日照・陰影

- 指定した地点や被写体に直射日光が当たる時間を知る。
- 時間とともに山の斜面、谷、湖面の明暗が変化する様子を視覚的に確認する。
- 順光・斜光・逆光や、山頂に最初／最後の光が当たる時刻を把握する。
- 空の明るさや色、薄明、朝夕の光の状態を推定する。

撮影者から太陽が見えることと、被写体に太陽光が届くことは別の問題として扱う。例えば、湖面が日陰でも遠方の山頂だけに光が残る状況を扱いたい。

### 3.3 気象・朝焼け・夕焼け

- 朝焼け・夕焼けが発生する可能性、時間帯、方角を予測する。
- 雲の高さ・厚さ・密度・分布、晴れ間を考慮する。単なる曇り予報でも、全面を覆う雲と疎らな厚い雲を区別したい。
- 観測地点の上空だけでなく、太陽から雲や地表に届く光の経路を考慮する。
- 予測の信頼度と不確実性を示す。
- 撮影計画の参考情報として、取得可能な気象情報（天候、気温、湿度、風向、風速、突風、降水、雲量、視程など）を指定地点・日時に対応して表示する。取得できない情報や予報対象期間外の情報は明示し、推測値を観測値として扱わない。

気象予測は地形・天体の幾何学的計算とは異なり、観測・予報データや予報時点に依存する。実現性、データの利用条件、費用、検証方法は別途調査する。

### 3.4 自然現象・水面・海岸

2026-11-26に追加する製品要件。初期公開までの実装を約束するものではない。

- 雲海：発生可能性・高度・時間帯・観測地点の探索。
- 霧・朝もや：発生可能性、分布、時間帯の推定。
- 露点・放射冷却：取得または推定できる関連気象情報の表示と、現象予測への利用。
- 大気の透明度：黄砂、PM2.5、エアロゾル、水蒸気等を考慮した遠景の視認性評価。
- 水鏡：風向・風速・水面の位置・地形・反射条件から、映り込みが成立する可能性を評価する。
- 潮汐・潮位：取得可能な観測・予測潮位、満潮・干潮時刻を地点・日時に応じて表示する。海岸地形との統合は追加検討。

天の川・星空と光害は3.1に記載する。雲海・霧・水鏡等は経験則だけで確定的な予報を行わず、物理的条件、データ範囲、信頼度を検証する。

## 4. 将来構想（未採用の提案）

光芒、月光による陰影、海岸地形と潮位の統合可視化、複数の光・気象・構図条件を組み合わせた撮影チャンス探索など。魅力のある候補だが、初期製品の必須条件には含めない。季節の見頃、積雪、日食・月食、流星群、アクセス情報等は今回の追加確定範囲外とし、必要に応じて再検討する。

## 5. 製品設計の原則

- **目的を優先する。** 機能の多さではなく、撮影に必要な判断ができることを評価する。
- **操作は単純にする。** 地点・視点、見る方向・画角、日時、光の条件を独立して操作できることを目指す。日時を変更しても意図しない構図変更を起こさない。
- **精度を優先する。** 特に日時・地点の逆算では、誤った撮影候補を提示しないよう、データの分解能・欠損・計算範囲・誤差の影響を示す。確定的な計算値、モデルによる近似、気象予測を区別する。
- **試行錯誤を快適にする。** 地形・天体の再計算と描画を分離し、操作への応答をできるだけ速くする。性能目標は5.2に示す。実装手法は開発側で比較・選定する。
- **アクセス可否を過度に断定しない。** 初期の地点逆算では曲線・地図情報を提供し、立入可能性、道路や登山道、安全性の確認は利用者に委ねる。
- **製品として成立させる。** 構想の全機能を完成させることを公開条件とせず、価値のある段階での公開・収益化を検討する。価格や無料・有料の境界は未決定。

### 5.1 空間表現と描画方式

- 夏季の高い太陽や天頂を含め、上下左右の全方位における地形・天体の位置関係を扱えること。
- 光の方向、地形による遮蔽、日照・陰影を空間的に表現できること。
- 内部の計算モデルを特定の投影・表示方式に依存させない設計を目指す。
- 見た目は現在のシンプルな2Dパノラマ（稜線と地形の重なり、距離による遠近表現）を基本として継承する。内部を3D化しても写実的な3Dゲーム風の表示に変更することを前提としない。
- 内部の3Dデータをそのまま操作させる3Dソフト風のUIではなく、観測地点から見える範囲を2Dの風景へ投影し、その風景を直接操作する感覚を優先する。ドラッグで見回し、ホイール・ピンチで画角を変更し、観測地点は地図のピンで移動する。内部の回転軸や3D座標を意識させない。
- 天頂付近まで見上げられ、視界の意図しない回転を避ける。必要に応じた俯瞰表示は設計候補。VR機器は必須としない。
- 山名・標高、稜線の輪郭線は独立した表示オプションとする。基本の風景を情報表示で埋め尽くさない。ズームや山頂選択に応じた表示密度、距離表示、山頂の遮蔽判定は設計時に検討する。
- 一日の天体軌跡を俯瞰する利便性と、自然な視野・高仰角の表現、精度、描画速度、メモリ・通信量を比較する。共通の3D世界モデルやGPU描画は設計候補であり、採用は未決定。

### 5.1.1 地図上の地平線表示（追加要件・訂正）

- 現在の観測地点を中心とし、地球曲率による幾何学的な地平線までの距離を地図上の円として表示する。円の外側を少し暗くする独立した表示オプションとする。
- 観測者の基準面からの高さ（地表標高と地上高を考慮）に応じて半径を更新する。初期は球面近似を候補とし、地図上では地理的な距離を用いる。大気差・基準面・楕円体の扱いは技術設計で明示する。
- 地形による実際の可視領域とは異なる。円内にも遮蔽物があり、円外でも標高の高い山頂等が見えることがある。円外を「不可視」と断定しない。
- 表示の暗さ・初期ON/OFFはUI設計で決める。

### 5.1.2 地図上の可視領域表示（追加機能候補）

- 地平線の円とは独立したON/OFFレイヤーとして、観測地点・視点高から地形によって遮られる地表を少し暗く表示する。遠方でも見える山頂・斜面は可視として扱う。地名・道路の判読性を維持する。
- 日照による影とは区別し、可視・不可視・未計算/資料不足を分ける。樹木・建物・特殊地形はデータの取得範囲に依存する。
- 第3回評議会のLOS/viewshed計算基盤を再利用する候補とする。観測地点・視点高・地形モデルの変更時に更新し、操作中の粗表示と停止後の詳細化を検討する。
- ユーザーが関心を示した追加機能として保持する。初期製品への搭載時期は計算負荷・メモリ・UIの検証後に判断し、単純な地平線表示の実装を妨げない。

### 5.1.3 地図を用いた光・地形・構図の探索（2026-11-27追加要件）

地図を地点指定だけでなく、稜線画面と双方向に連動する解析・探索画面として扱う。以下を製品仕様の対象に追加する。実装時期・探索UI・計算精度の採用基準は未決定。

| 機能 | 表示・操作 |
|---|---|
| 可視領域 | 5.1.2の可視域レイヤーを実装対象に含める。地平線円とは独立。 |
| 日照・陰影 | 選択日時に応じて地表の直射日光と地形影を地図上で更新する。観測者からの可視性とは区別。 |
| 逆可視領域 | 被写体・山頂等を指定し、それが見える観測地点を地図上に表示する。両端高さ・地形欠損を考慮。 |
| 撮影適地 | 構図、被写体の可視性、光の方向、遮蔽物、利用可能な気象情報等を組み合わせ、候補地点・日時を可視化する。評価根拠と未計算を明示し、初期は立入可否を保証しない。 |
| 太陽・月の方位軌跡 | 観測点から時刻別の方位線を表示する。方位線だけで重なり・天体可視を断定しない。 |
| 地形断面 | 地図上の2地点間の標高・視線・遮蔽物を断面で確認する。 |
| 地図と稜線の双方向選択 | 稜線上の山頂・地形点と地図上の対応点を相互に強調。位置・距離・遮蔽・同定の不確実性を考慮する。 |

各レイヤーは独立して切替可能にし、時間・地点・視点高・画角を共通状態で管理する。探索結果のUIは実際の計算機能を接続した後に設計する。共通天球投影では、高仰角・天頂付近で単純な水平方位目盛りが誤解を生まないよう、方位・高度座標線の投影または非表示を検討する。

### 5.2 リアルタイム操作・性能

- 方位・仰角、ズーム、日付、時刻、視点高の変更、および必要な地形データが取得済みの範囲での観測地点移動は60fpsを目標とする。
- 地図上の観測地点をドラッグしている最中も、風景を連続的に更新できることを目指す。観測地点に依存しない地形保持やGPU描画、キャッシュ等の採用は技術設計で判断する。
- 未取得地域・詳細度の不足によるデータ取得待ちは許容する。取得状態・暫定表示を明示する。
- 描画の解像度・詳細度と、撮影地点・日時の逆算や遮蔽判定に必要な計算精度を区別する。描画速度のために最終計算精度を無断で落とさない。
- 60fpsは性能目標であり、対応機種、計測条件、実機での達成可否は未検証。

### 5.3 スマートフォン対応

PCとスマートフォンを設計当初から対象とする。スマートフォンではタッチ操作（ドラッグ、スワイプ、ピンチ）、縦・横画面の利用を考慮する。現地利用を支援するGPS、方位センサー、取得済みデータのオフライン利用は設計候補として検討し、端末の制約や権限、容量を検証する。PWA・WebGL 2等は候補であり採用未定。

### 5.4 時間操作・タイムライン（設計候補）

- 地図・2D風景・時間操作を共通の観測地点、構図、日付、時刻に連動させる。
- TPEの時系列表示を参考に、動画編集ソフトに似たマルチトラックタイムラインを検討する。瞬間イベントはマーカー、継続する現象は区間、気象の可能性は不確実性を示す帯、気象量や潮位等はグラフで表現する。
- 太陽・月の可視区間と被写体の日照区間を区別する。天文上の日出・日没、地形遮蔽、薄明、ゴールデンアワー等の定義の違いを明示する。単なるスコアを校正済み確率と混同しない。
- 再生ヘッドで風景・地図・気象表示を同期し、必要なトラックだけ表示できる構成を検討する。PCとスマートフォンの画面構成、時間軸の拡大、日付スライダーの開始・終了日指定はUI設計で決定する。
- 説明書なしで基本操作を開始でき、詳細機能は必要時に展開することを目指す。基本風景の無料体験・登録なしの導入は収益化設計の有力候補であり、課金範囲は未確定。

### 5.5 通常UIの設計基準（第6回、2026-11-27）
通常操作UIの設計は一区切り。詳細は[第6回UI/UX仕様](technical-design-council-06.md)、基準試作はUI Lab v0.24（本体v0.10とは別）。スマホの上下2画面と切替、PCの左右分割ドラッグ、上部探索/設定、設定内タブ、中央固定時間軸、稜線下端の方位目盛り、太陽の直接操作、地表標高と視点高、詳細情報のコンパクト化を継承する。探索UIは実機能の接続後に決定する。天頂付近の方位高度座標表示は共通投影で検討。試作の模式値や暫定実装は製品の計算仕様を置き換えない。

## 6. 現在地と検証上の留意点

v0.10は可能性を検証するプロトタイプ。地点・日付・時刻指定、地形・太陽軌跡の表示、遮蔽推定、全方位パン、ズーム、日付スライダー、期間内の軌跡重ね表示を実装している。G1・G2は試作段階、G3は手動探索の補助まで、G4・G5は未実装。

丹沢湖での試用では、地形の見た目に良好な手応えがあり、2027年3月6日がダイヤモンド富士の撮影候補として見つかった。ただし、撮影地点・視点高の確定と独立した精度検証は済んでいないため、日時や標高の正解データとしては採用しない。

日付範囲の重ね表示は操作が複雑になる可能性があり、開始日・終了日を指定する単一日付スライダーへの簡素化を検討する。既存実装はこの資料の作成時点では変更しない。

## 7. 次の設計段階で決めること

1. 各目的の具体的な成立条件と、必要な入力・出力。
2. 競合製品・市場調査に基づく初期製品の範囲、優先順位、公開時点の価値。
3. UI・UXの全体構成と操作体系（既存機能の整理を含む）。
4. 地形・天体・逆算・描画・日照・気象の責務分離。
5. 精度・応答速度・データ費用の目標、検証計画。
6. 収益化と市場需要の検証。

実装の再開や機能削除は、この資料では決定しない。
