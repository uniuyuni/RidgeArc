## 0. 評議会の位置づけ

地理空間・測地学、天文学、光学・大気物理、GPU・描画、ソフトウェア設計、検証・反証、議長の7視点を単一AIが順次担当。独立したAI間の合議や外部専門家レビューではない。以下の選定は暫定。既存製品要件（2D風景の直接操作、取得済み範囲内の地点ドラッグ60fps目標、スマホ対応、自然現象の追加）を維持し、製品優先順位・公開範囲・課金を決定しない。

## 1. 現状評価

core.mjs / app.mjs / tests/core.test.mjs と既存資料を確認した。現状は観測点依存の放射状標高配列、0.25度の方位間隔、最大70km、球面曲率近似、JST固定の太陽近似式、離散円盤サンプル、15秒走査と1秒の数値絞り込み、Canvas 2Dの環状パノラマ。高さ・日付・パンでのデータ再利用は成果。地図ピン移動はdragend時の再計算で、取得済み地形であっても全操作60fpsを満たす構造ではない。

既存accuracy-validation.mdでは丹沢湖の2km内の限定295/1440方位で、2m間隔と試作の動径サンプル間隔の比較にMAE 0.01264度、p95 0.07679度、最大0.25867度の差があった。同じ地形資料によるサンプリング差であり実景誤差ではない。過去の太陽式検証も限定3日・地点であり、月・大気差・現行実装の全域精度は未証明。

判断：既存画面の風景表現と試験を維持する。地形取得・計算・表示の内部は再設計候補とし、直ちに全面書き直さない。

## 2. 地理空間・測地学

### 2.1 観測点非依存の共有地形

元の高さデータを地理タイル/領域で保持し、観測点から見える地形と各地点の日照の両方に再利用する。地理座標、標高基準、データ版・測量時期、元の解像度、補間法、欠損マスク、誤差情報を保持する。裸地DEM、DSM、建物・植生、水面、欠損・範囲外は別レイヤー。海面と欠損を同一の0mにしない。樹木・建物のない裸地モデルを現実の完全な遮蔽と混同しない。

日本の入力候補はGSI DEM1A > 5A > 5B > 5C > 10B（利用可能範囲による）。最大ズームの標高タイル自体にも平滑化があり、低ズームは平均化される。精密な比較には元の基盤地図情報も使う。1A/5Aの0.3m以内という標準偏差は計測点がある条件で、ない場合は2m以内。10Bは5m以内。標準偏差は厳密な誤差上限ではない。海外はCopernicus GLO-30等の候補を別途比較する（DSMで裸地との意味が異なる）。最初の技術検証は国内を対象にし、海外展開を製品判断として固定しない。

精度経路の原始地形には、再構成したセル面の最小・最大標高、欠損、位置境界を持つ階層（quadtree / min-max pyramid）を作る。粗い標高の平均値だけで遮蔽を否定しない。上限角が既知の地平線より確実に小さい領域を飛ばし、候補となるセルを細分化する。上限はデータ上の面・楕円体変換・誤差条件に対して保守的であることをテストする。領域全体の標高最大だけで正確な稜線とみなさない。セル面の補間（初期は固定三角形分割または双線形を比較）を明示し、参照計算と描画の基準面を揃える。欠損の上限が不明なら判定不能として残す。

### 2.2 座標と高さ

内部は度/ラジアンとmを明示、倍精度の地理座標/地心地球固定座標(ECEF)を用い、観測点・タイル近傍でENU（東・北・上）に変換。GSIはJGD2024/GRS80及び以前の測地成果も含むため、元データの水平・鉛直基準と版を記録して変換する。標高Hと楕円体高hは同一ではない。h=H+N（適切なジオイド・離島等の基準面補正を確認）。地図のWeb Mercatorは検索表示・入力用であり距離/角度計算の正解としない。地球曲率は座標変換に含め、同じ補正を二重に適用しない。精密計算にGPUの地心float32絶対座標を使わず、タイル相対座標/原点再設定を用いる。

観測点の高さは地表標高、地上高、絶対標高の指定方法を区別する。対象点の水平位置・高度も独立。観測者と山頂の相互位置の誤差は距離に依存して角度誤差になる。例：垂直誤差1m/距離100mは約0.57度（小角近似）。近景の障害物・カメラ高さを過小評価しない。

### 2.3 範囲・解像度・通信

70kmを物理的な可視限界としない。必要範囲は観測高度、対象標高、曲率、屈折モデル、使用可能な地形の保守的な上限に応じて判断する。範囲外に遮蔽物がないことが確立しなければ「取得範囲内の結果」と表示。最大探索範囲/通信予算に達したら未確定とする。

140km四方を全て10m格子・float32で保持すると約784MB（メタデータやGPU複製を除く）、1mなら約78.4GB。単純な全解像度ロードは却下。精度に寄与する近景・稜線・被写体から優先し、広域の粗い階層と必要な詳細タイルを組み合わせる。データ取得済みとCPU/GPU常駐済みを区別する。表示のLODは画面誤差で、解析のLODは角度/遮蔽の誤差条件で選ぶ。GSIへの直接アクセス/前処理・再配信/ローカルキャッシュの可否は利用条件、出典、測量法、負荷、費用を確認してから決定。

## 3. 天文学

Astronomy Engine（JS、MIT、公称1分角以内）を第一評価候補。太陽だけのNREL SPA（論文公称0.0003度）、JPL Horizonsのairless topocentric出力を独立比較の候補にする。SPA実装コードの商用利用条件と検証データ利用条件は別途確認。公称値は採用基準の実測ではない。JPL APIは実行時依存ではなく、回帰試験用の参照として使う。

天体の中心方向（単位ベクトル）、距離、視半径、月相/明暗境界、幾何学高度と屈折補正高度を区別。太陽・月は観測地点基準のtopocentric計算（特に月視差）、観測時刻、地球回転・時刻系を扱う。内部時刻はUTCインスタントとし、ローカル日付/タイムゾーンは別、UTC/TT/UT1等の変換を採用ライブラリの規約に合わせる。海外・日付境界・DST・極域・北越えをテスト。天の川は単一点でなく銀河座標系の帯/輝度分布として方向変換する（星カタログや画像のライセンスは後続調査）。

大気差は幾何学結果と別モジュールにする。気圧・気温・高度・標準大気/実測の設定と不確実性を保存する。円盤の上端・下端の差動屈折も精密化候補。近地平線の強い大気差や異常屈折は保証外として明示。地形の光路屈折と天体の屈折は異なるので、一定有効地球半径を天体にも適用する等の二重補正を避ける。

## 4. 遮蔽・逆算（G1〜G5）

### 4.1 共通述語

TerrainHorizon(observer, azimuth, model) は幾何学/屈折設定を明示した地形仰角・距離・遮蔽物ID・資料範囲・品質を返す。TerrainLOS(observer,target) は被写体までの線分遮蔽、RayHit は最初の地形交点。被写体より後ろの山による被写体遮蔽の誤判定を避ける。

可視判定は画面上のピクセルではなく角度空間・単位方向ベクトルで行う。地形を連続面として定義し、太陽/月円盤全体と稜線の交差を求める。幾何学的に光球円盤が見える割合と月の明部・雲の遮蔽・大気透過は別。
円盤各方向の稜線に対する余裕 g=高度-稜線高度 を考え、max(g)>0なら一部可視、min(g)>0なら全体可視（接触の扱いは境界イベント）。0付近は角度誤差や接線を考慮する。データ欠損は可視/遮蔽/不明を分離し、確率と混同しない。

### 4.2 G1 / G2 固定観測点

全方位稜線と距離/最初の交点を共通地形から生成する。全出現・部分遮蔽・完全遮蔽・再出現をイベントと区間として返す。固定間隔の端点符号だけでは短い遮蔽/再出現や接線を落とすため、時間/方位区間で太陽円盤の角度範囲と稜線の上限下限を比較して再分割する。根を囲めた場合は二分法/Brent法等で精密化、接線や複数根の可能性も扱う。保証できない区間は未解決として返す。精密化1秒は数値停止条件であり現実の時間精度ではない。固定観測点の稜線キャッシュは日付変更で再利用。

G2は同一の地形面・天体方向を2D投影する。解析用稜線と描画稜線の差が許容を超える場合は詳細化・暫定表示。GPU深度の見た目だけで接触を決定しない。

### 4.3 G3 日時逆算

固定観測点、目標方向/被写体、対象天体、許容角度、探索期間、朝夕/接触条件を入力。画面上で選択した位置を世界方向へ逆投影して固定する。各日で目標方向との球面角距離（または所定の方位/仰角オフセット）を評価し、粗探索→局所最小化→連続時間の候補区間→遮蔽検証。日の出だけでなく山頂と天体の中心一致、円盤縁の接触等は条件を分ける。全日程を対象とし、極値・接線・複数候補を落とさないため区間枝刈りを検討。検証していない完全探索を約束しない。日付スライダーの手動探索を残し、自動候補を日付・時刻・角度誤差・可視性で返す。

### 4.4 G4 地平線まで沈む場所

「天文上の日没が見える」「地形で隠れない」「海の水平線に沈む」は異なる。
仮仕様：指定地域・日付で、地球曲率と観測高度・基準水面および屈折モデルから求める基準地平線への上端の最終接触を、他の地形に遮られず見届けられる場所を探索する。既知の海域/水面による水平線を求める選択肢を分離。さらに最後の一定時間または円盤が基準地平線へ接触し始めてから消えるまで連続して見える条件を選べるようにする。何分前から、どの可視率を必要とするかは未決定。欠損・距離範囲・裸地と樹木等は明示する。

地域を階層セルに分割し、時刻・方向の粗評価から確実に不適格といえる領域を除き、残りを詳細評価する。候補地点では実際の太陽経路に沿って円盤と地形を連続評価。粗い観測点格子だけでは数m幅の尾根や道路を落とす。十分に保守的な地域セルの判定が作れない場合は、探索間隔を明示したサンプルベース探索とする。結果：条件成立候補 / モデル内で不成立 / 未評価・不明領域。該当点なしは探索範囲・精度・判定条件付きでのみ表明。

### 4.5 G5 撮影地点・日時逆算

被写体の位置と標高、探索範囲/距離、日付範囲、天体、位置関係（中心・縁・左右上下オフセット等）、許容角度、観測者地上高を入力。

第一案：対象の周囲を距離と方位（または地域セル）でパラメータ化。各地点の地表高と観測高を求め、被写体方向・太陽/月の方向との差を評価する。日ごとに天体の方位一致に近い時刻を解き、その時刻の仰角差を求める方法を高速化候補とする（方位解の複数・不存在、天頂付近、接線に注意。一般経路は球面角距離を最小化）。仰角差ゼロの等値線、許容角度内の領域を抽出し、近接した枝や閉曲線も扱う。直線/曲線/面/孤立点のいずれもあり得る。粗探索後に候補と不確定領域を細分化、全ての出力点で時刻・角度・被写体までのLOS・天体可視性を再評価。被写体へのLOSと太陽の可視性は別。ダイヤモンド富士では円盤が一部山に隠れる構図を許すので全面可視を一律必須にしない。期間の候補線・帯を日付で識別し、選択地点と時刻と2D風景を同期。土地の立入・道路アクセス・安全は初期には判定しない。

比較案：全地点×全時刻の総当たり（小領域の検証参照、広域には高コスト）、被写体から天体方向への逆光線を地表と交差させる方法（固定時刻・幾何条件の候補生成に有用、天体方向の位置依存・観測高・屈折・地表の複雑さに注意）。一つの高速近似を完全解とみなさず、合成地形の総当たりと参照ソルバーで検証する。

## 5. 光学・大気物理

地形の形状と直射光・散乱光・大気遠近・表面反射を分離。観測者の太陽可視性は被写体の照明とは異なる。被写体点/地表点それぞれから太陽方向への遮蔽と法線の入射角を評価。直射照度は可視円盤割合と入射角、透過率等から推定する（厳密には円盤内の積分）。描画用のシャドウマップ、必要に応じた地形面法線を使う。撮影対象の精密日照時刻は解析経路で検証する。GPUの影だけを物理予報としない。

空の明るさと色、霞を表現する場合は太陽高度・視線方向・大気モデルから算出する。描画色は美的な表現と物理的放射量を区別し、実写色/露出の再現を保証しない。雲海・霧・夕焼け・水鏡等は別の予報プラグイン。観測・予報モデルの初期時刻、対象時刻、空間高度、取得範囲、信頼性、出典を保持し、後日個別に研究。湖の水鏡は水域・反射光路・風/波等が必要、地形に鏡面反射を描くだけでは予測にならない。潮位は基準面と観測所・予測/実測を保持。天文計算と同じ時刻で同期するが、同じ精度・将来範囲では扱わない。

## 6. GPU・描画技術

3Dデータのレンダリングを内部に採用しても、ユーザー操作は観測地点から投影された2D風景のみ。回転・パンは見る方向、ズームは画角、地図ピンは観測点、時間は光と天体。既存の距離色と空気遠近の見た目を維持。山名・稜線輪郭は独立オプション、山名の被写体位置の遮蔽はLOSで検証。山頂データの利用条件は別途調査。

| 描画候補 | 利点 | 欠点 |
|---|---|---|
| 現行の放射状断面+Canvas2D | 実績・既存UIを保持 | 地点移動時の再計算、角度解像度 |
| タイル化した高さ場のGPUメッシュ | 地点移動時に再利用、深度/距離/法線、ラスタライズ | LOD境界、メモリ、極端に広い画角、遠近精度 |
| GPU高さ場レイキャスト | 一方向ごとの直接交差・柔軟な投影 | ピクセル数×探索負荷、端末差、複雑 |
| 既存汎用3D地形エンジン | タイル管理などの既存技術 | 制御・重量・配布費用/ライセンス・2D表示適合性 |

第一試験案：WebGL2のタイルメッシュ（quadtree/geometry clipmapの考え方）+ 解析用CPU階層。必要に応じてGPUレイキャストと比較。地形面の形状をノイズ等で捏造するディテール生成は精密用途に採用しない。単一透視投影では180度以上と天頂近傍の全天を表せない。広角パノラマは複数方向の透視レンダリングから球面/円筒へ再投影する案と直接高さ場投影を比較。現行Mercator型は天頂で発散するため、天頂を含む表示の投影設計は別の検証課題。画像の見かけと計算の角度座標は分離する。

60fps（16.7ms/frame）は取得済みかつ必要LODが処理可能な条件での目標。GPUに常駐した地形で視点更新し、重い探索はWorkerで処理、最新要求優先・キャンセル・古い結果の適用拒否。表示中の近似LODと確定解析を区別し、ドラッグ中でも可能な範囲で現在地点の暫定風景を更新。地形メモリとGPUメモリ上限、転送、端末発熱、WebGL context lostからの回復を計測。60fpsを得るために最終解析精度を落とさない。固定タイムライン更新で地形タイルを再取得しない。WebGPU/WASM/OffscreenCanvasは測定結果に応じて採用し、必須機能への互換性を実機で確認する。

## 7. ソフトウェア設計

暫定的にブラウザ/PWAを第一候補とし、現行静的配布とクライアント計算を活用。フレームワーク変更は決めない。以下は責務境界であり、それぞれ別プロセスやマイクロサービスにする必要はない。

- GeoTime：座標/高さ/時刻/方向、誤差・基準の型。
- TerrainStore：入力タイル、原始データ、階層、欠損、キャッシュ、ソース版。
- Geometry：RayHit、Horizon、LOS、地形面法線。
- Ephemeris：天体の方向・円盤・時刻。
- Visibility/Light：円盤・地形遮蔽、イベント、被写体日照。
- Search：G3〜G5の候補生成、検証、結果領域と未評価範囲。
- Environment：気象・大気・水域・潮位・光害等のアダプタ。
- Renderer：SceneStateからの2D風景、オーバーレイ、暫定LOD。
- UI：地点・構図・時間の単一状態、地図・風景・タイムラインの同期。

結果データは数値に加え、単位・座標基準、観測/予報/計算区別、モデル版、資料の出典・時刻・範囲、欠損、誤差の種類、暫定/確定状態を返す。検索結果と描画は同じSceneStateの世代番号とTerrainVersionを持ち、更新競合を避ける。イベントは点/区間、時系列はサンプル/補間定義を持つ共通契約。タイムラインの濃淡は校正済み確率と未校正スコアを区別する。

通信・永続化は階層LOD、LRU、メモリとストレージの個別予算、再試行、取得状況、オフライン準備済み領域の表示を採用候補とする。公開DEMの大規模先読み、独自CDN・全世界タイル前処理、サーバ計算の必要性は利用条件・運用原価調査まで保留。環境データの秘密鍵はクライアントに置かない。個人の観測地点の外部送信は必要な範囲に限定。独自サーバ必須化を避け、広域長期探索等が端末限界を超えるときのみ選択肢を比較する。

## 8. 反証役と議長

| 反証 | 対応 |
|---|---|
| 1m DEMの精度を信用し過ぎている | 裸地・測定点・境界・平滑化・位置/高さ誤差を分離。実景と照合 |
| 粗い地形で高速に描画できても山頂が消える | 描画LODと保守的な解析階層を分離。確定時には照合 |
| GPUとCPUの別エンジンが矛盾する | 同じ原始地形/面/座標/版を共有。接触時の表示差を試験 |
| 60fpsのため全地域を常駐させるとスマホが破綻する | 可視範囲・詳細度・明示的なメモリ予算、取得済みと常駐を区別 |
| 広域探索で隠れた解を見落とす | 保守的な区間枝刈り、未解決領域の表示、参照総当たりとの比較 |
| 高精度天体式で時刻まで保証してしまう | 数値収束と物理不確実性を別に評価。地平線付近は特に注意 |
| 将来機能のため過剰に抽象化する | 具体的なG1/G2の縦断プロトタイプで責務境界を確かめる。気象等は必要なデータ契約だけ |
| 既存コードを捨てるコスト | 現行を比較基準として残す。検証用の計算とUIを段階置換 |

議長の暫定統合案：**地理的に固定された共有地形、多解像度の階層、解析（真値を目指す）と描画（即時応答）の二経路、共通の座標・時刻・データ版**。G1〜G5を同じ述語で扱う。JS/WebGL2を最初に評価し、WASMやサーバ化は性能測定後に決定。既存の2D体験を失う設計は採用しない。

## 9. 検証計画と次の判定

既存accuracy-validation.mdの数値基準は履歴として保存。次の数値は暫定目標であり保証値ではない。

| 指標 | 初期評価基準 |
|---|---|
| 天体の幾何学方向 | 既存0.02度以内を最低の比較基準とし、0.01度を改善目標として太陽/月別に評価。球面角距離、月距離・視半径も比較 |
| 稜線 | 同一入力地形面の密な参照と比較し、p95 0.05度を改善目標。局所最大、接触方位、被写体方位を個別評価。現実との誤差と分ける |
| 接触時刻 | 同じ地形面・天体モデルの独立参照との数値差1秒を目標（接線/不明区間を別扱い）。好条件での実測30秒以内は探索的目標、物理精度保証ではない |
| G3/G4/G5 | 合成地形の既知解・密な総当たりと比較、返却候補の再評価、偽陽性・偽陰性と未解決面積を記録 |
| 操作 | 60Hz端末でフレーム時間中央値/p95/p99、1% low、入力から新しい地点の描画まで、解析確定までを計測。p95 16.7msを初期目標。古いフレーム表示で数値を稼がない |
| 資源 | 初回/再訪の転送量、CPU/GPU推定メモリ、端末発熱、連続操作時、ストレージ、キャッシュ破棄、欠損挙動 |

検証順序：
A. 合成平面・単一山・二重稜線・細い尾根・欠損・タイル境界・海面、接線/短い再出現、日付境界。
B. 既存丹沢湖DEMの再比較、可能なら同一地点・高さの完全なDEM取得と独立参照。HORAYZON/GRASS GIS、JPL Horizons/SPA等を開発時参照に評価。ライセンス確認、実行環境構築は未実施。
C. GPUメッシュと現行方式の小規模技術スパイクを作る計画を立てる。視点移動・パン・時刻を別々/同時に計測。Mac M1、実機Android、可能なiOS/Safariで比較。スマホ機種や試験条件は未指定。
D. 逆算を小領域で総当たりと照合し、地域/期間の拡張時に処理量と探索取りこぼしを測る。G4/G5の条件選択と未知領域の契約を検証。
E. 実景で観測地点・高さ・日時・カメラ画角・方向・樹木/建物・気象条件を記録し、稜線角と円盤接触を比較。丹沢湖の従来写真は地点未確定なので正解値として使用しない。

この回では試験実行・ソフトの実装は行っていない。次回はデータ取得/キャッシュ・GPU投影を比較し、実験計画の対象機種・シーン・費用・合格基準を詰める。気象・光学の現象別予報、山名データ、収益化、UIレイアウトは後続設計で扱う。G4の基準地平線・連続可視の条件、G5の縁/中心、許容角度は仮仕様として利用者と確認可能な状態に残す。
