前提：[第1回評議会](technical-design-council-01.md) / [製品構想](product-vision.md)

## 1. 地形データ担当：地理タイルと表示パッチの分離

入力タイルは観測地点に依存しない。GSIのDEM1A/5A/5B/5C/10B、元解像度、取得日時、版、座標・高さ基準、欠損を保持する。最大ズームはDEM1A z17、5m系 z15、10B z14。低ズームの平滑化された標高を精密解析の上限/下限として使わない。基盤地図情報の元データとの比較は第1回の計画を継続する。

ソースキーは source/version/z/x/y。派生データキーは元タイル群、変換/補間/メッシュ生成の版を含む。ソースの優先順位は取得時点の実際の整備範囲・品質に従う。同じ点の高低解像度の値が異なる場合、描画の境界処理と精密解析の原始値を分け、任意の標高オフセットを解析に流用しない。タイル境界は隣接サンプルを取得し、重複する辺の位置・高さを同じ規則で生成。欠損は海面として補完しない。

内部は三層：
- 永続キャッシュ：取得元の圧縮タイル/許諾された加工データ。領域マニフェスト、出典、版、検証情報を持つ。
- CPU：デコード済みFloat32標高（座標変換はFloat64）、欠損マスク、セル上限下限階層、必要なら誤差階層。解析Workerが所有、コピーを避ける。
- GPU：必要な描画パッチの高さテクスチャ、欠損マスク/頂点インデックス、タイル相対座標。解析の真値ではない。画角/地点変更で再利用。

保存済み、CPU準備済み、GPU常駐、精密解析に必要な範囲完備はそれぞれ別の状態。GPUにないタイルのロードはあり得るが、取得済み領域内では粗い親パッチを再利用して現在視点を表示し、優先度を付けて詳細化する。旧地点の画像を新地点として表示しない。

### 1.1 容量のモデル（実測ではない）

理想的な重複を含む正方形の格子モデル、端点を省略した概算、各標高4 byte：
| 領域幅 | 格子間隔 | 標高値容量 |
|---|---:|---:|
| 2km | 1m | 16MB |
| 10km | 5m | 16MB |
| 40km | 20m | 16MB |
| 160km | 80m | 16MB |
| 合計 | | 64MB |

20/80mは設計上の例であってGSIの製品名ではない。距離リング固定方式の採用ではなく、メモリ規模の説明用。必要な遠方山頂は高詳細タイルを追加する。160km四方は必要可視範囲の上限ではない。

256x256のfloat32標高は256KiB、1byte/点欠損は64KiB。192枚なら60MiB。2x2縮約の親階層にmin/maxをfloat32で両方保持すると、親階層だけで約32MiB追加（葉の標高と欠損は既存、階層の欠損/誤差メタデータ別）。GPUに96枚の高さ値だけを置くなら24MiB。1600x900のRGBA8色+32bit相当の深度は約11MiB/組。GPU実消費量、ブラウザ、地図、アップロード一時領域、解析結果、複製、追加バッファは別途必要。PCも統合メモリのためGPUを別の無制限領域とみなさない。

実測前のアプリ管理予算の初期設定案：スマホCPU標高等64MiB、GPU地形32MiB、描画ターゲット24MiB、PCはCPU128MiB、GPU地形64MiB、描画ターゲット48MiB。上記192枚+階層はスマホCPU予算に収まらないので、原則として階層を含むバイト数でLRU制御、必要なら枚数/解像度を落とす。予算は端末能力を保証しない。ブラウザ全体のメモリを正確に取得できない場合は自前割当とOS/ブラウザの計測を併用。精密解析に必要なデータが不足する場合は分割処理または未確定を返す。

## 2. データ取得・通信担当

GSI標高PNGを最初の入力候補とする。取得済みデータを地点変更で再利用。全日本の先読みは行わず、次の要求を優先する。
1. 観測点の正しい地表高と近傍、現在画角の粗い地形。
2. 現在画角の稜線・接触方向・対象山頂の詳細。精密解析に必要な画角外の候補も別キュー。
3. 周辺移動に備える近傍の親タイル・方向外の粗い地形。
4. ユーザーが明示したオフライン領域。

HTTP要求を重複排除し、並列数は暫定4、2/4/8を比較。AbortControllerで不要な要求を取り消せるようにするが、他の要求と共有中の通信は中断しない。404/範囲外/欠損/429/一時障害を区別し、Retry-Afterがあれば従う。ネットワーク再試行の間隔・上限を設定。ドラッグ毎にリクエストを発生させない。低詳細度から表示し、優先度を変える。通信量は実ファイルのContent-Lengthや実転送サイズで測る。仮に40KiB/タイルを256枚取得した場合10MiB（単なる例、圧縮率の実測なし）。同じデータでの再訪時はキャッシュの版/有効性を確認し、再取得を最小化する。

ブラウザ永続化の候補はIndexedDB（バイナリ+マニフェスト）、Cache API（HTTPレスポンス）、必要時にOPFS。最初は二重保存を避ける。容量をStorageManager.estimateで概算し、persistの結果を確認。容量不足、ブラウザによる退避/消去、Safariの制約を考慮し、永続化を保証しない。オフライン画面は保存済み範囲、使用可能な精度、取得時刻、必要量/空き、削除を明示する。通信がないときの再起動で領域が使用できることを実機で確認。

国土地理院利用規約は原則PDL1.0を適用する一方で、測量成果の複製/使用の申請が必要な場合もある。出典・加工表示の要件を守る。直接利用、個人端末キャッシュ、オフライン配布、加工タイルの商用再配信それぞれについて適用条項、申請要否、アクセス負荷を確認してから公開。公開データであることを無制限の大量取得/再配信許可とみなさない。独自配信/CDN契約は未決定。現時点では利用許諾を取得したわけではない。

## 3. GPU描画担当：比較案と試験順序

A. 地理タイルに対応する正則パッチ（第一候補）。65x65頂点、64x64セル、8192三角形/パッチ。32/64/128セルを比較。固定インデックスとUVを共有し、頂点シェーダーで高さを参照。96パッチなら全パッチ描画時約78.6万三角形/パス。これを速度の保証としない。視錐台/地平線カリング、LOD制御、描画バッチ化、必要ならパッチサイズを変更。CPU地心倍精度/タイルローカルGPU座標。欠損を無効にする方法はパッチ分割、マスク、セルの除外を比較。高さテクスチャはR32F等を試すが、浮動小数点色バッファや線形フィルタ拡張を必須にしない。手動補間と頂点取得を評価する。

B. Geometry Clipmaps。固定の入れ子格子を観測点近傍で移動し、新しく入る領域のみ更新する。GPUベースの既存技術を参照。大きな連続格子での描画効率が利点だが、複数ソース境界・方向別詳細化・遠方の細い稜線・欠損の管理は追加設計が必要。まずAを検証し、パッチ管理/アップロード/描画呼出がボトルネックならBを比較。平均化したクリップマップを遮蔽の精密解に流用しない。

C. 高さ場GPUレイキャスト。ピクセルごとに階層を走査、広角投影と first-hit に向くがピクセル数とレイ反復で負荷が変動。Aでパノラマの継ぎ目/描画速度を解決できない場合に試す。D. Cesium等の既存エンジンは地形LOD・深度技術の比較対象。既存の2D操作・見た目・独自DEM・バンドルサイズ・利用条件に適合するか確認するまで製品採用しない。

LOD：距離だけでなくパッチの幾何誤差と画角から画面誤差を推定。1〜2pxを描画精細化の試験初期値とする。遠い富士山の山頂・接触方向は優先度を上げる。分割/統合にヒステリシスを設け、親子の同時描画によるZ-fighting、継ぎ目/偽の稜線、切り替え時のポッピングを検証。LOD遷移は描画に限定。精密解析では元地形のセル上限下限で枝刈りし、上限が未知なら不明。既存の0.25度角度格子固定を撤廃する設計とし、最終角度精度を独立評価。

## 4. 2D投影と風景表現担当

UIの状態は観測点、地上高/絶対高、方位、仰角、画角、日時、表示オプションのみ。ロールを原則固定し、地形中心の回転・軌道カメラ・3D軸をユーザーに要求しない。ポインター/タッチで風景を直接操作。天頂で方位が特異になるため、方向ベクトルと画面の上方向を内部で連続保持し、真上を越える操作の挙動を実機で決める。

投影は視線方向を共通に扱う。通常画角では透視投影、広い一日軌跡では円筒/球面パノラマ候補。画角の変更だけで投影が予期せず切り替わらないようにする。広角は複数の透視画像を2D角度座標に再投影する方法を先に評価。全6面を毎フレーム更新する方式は初期案から除外。現在見えている範囲と必要な隣接セクタを描画し、固定観測点・地形版・投影・解像度でキャッシュ。高仰角と天頂をMercatorの無限拡大/クランプだけで表現しない。全方位・天頂・北境界・ズームアンカーを試験。2Dの軌跡、山名、稜線、天体円盤を同じ方向投影で合成する。

近距離1m級から100km以上の描画では通常の深度バッファの遠近精度が問題になる。近クリップ距離を必要以上に短くしない。カメラ相対座標、対数深度/距離分割を比較し、同じ画素で近い地形が必ず手前になることを確認。Cesiumのmulti-frustum/log depthは参考であり、そのまま採用するとは限らない。稜線・細い山頂の見落としとGLの同期readPixelsコストを避ける。精密な可視性はCPUの解析経路を用いる。

描画はまず現行の距離に応じた色彩・空気遠近法を再現。地形の輪郭線と山名は個別オプション。地形が固定されている間は、距離/法線等の補助バッファを必要に応じ保持し、時刻の変化は太陽・月・空・陰影に関する処理のみ更新。日照影の変化で再計算が必要な場合は区別する。初期スパイクは距離色と天体を対象にし、後続の日照/気象描画を同時に60fps達成とみなさない。美的な配色は照度や大気透過率そのものではない。

## 5. スケジューリング担当

UIスレッドはイベントを最新状態に集約しrequestAnimationFrameで描画。地形の解析・デコード/変換/階層構築はWorker。Transferable等で大きな配列コピーを抑制する。Workerが保持する精密タイルを転送で失わない所有規約を用意する。SharedArrayBuffer/OffscreenCanvasは必須にしない。画像のデコードとGPUアップロードのバッチを計測し、フレーム負荷に応じて制限。重い解析は分割実行・キャンセル可能。更新要求の世代番号、地形版、座標基準、カメラ状態で古い結果を排除する。表示の暫定/精密結果の確定を独立に管理。

60Hzの16.67msの暫定配分（計測用の予算、CPUとGPUは並行動作するため単純加算は実測時間ではない）：UI・地図・状態更新2ms、LOD選択/GL提出3ms、GPU描画8ms、アップロード/余裕3.7ms。GPU時間はEXT_disjoint_timer_query_webgl2があれば非同期測定、なければフレーム間隔等を使用。CPU送信時間だけでGPU負荷を判断しない。高DPIスマホは内部描画解像度を調整してUI文字・精密結果の精度を落とさない。60fpsを得られない場合は画面解像度、描画パッチ/LOD、追加効果を調整し、欠損や確定結果を捏造しない。

## 6. 反証担当

- 64MBの標高モデルは原始値だけであり、要求数/復号/階層/GL複製/ブラウザの総メモリを無視すると破綻する。バイト予算・実機測定で反証する。
- GPUが速くてもUIや地図、通信、タイル更新が詰まる。キャッシュ済み/冷起動/欠損を分けて測る。
- 近景1mでも遠方の鋭い稜線を粗視化すると位置がずれる。画面誤差と解析誤差を分離し、重要方向を精密化する。
- 6面パノラマは単一パスの倍以上の処理量になり得る。可視セクタだけ、キャッシュ、直接投影と比較する。
- WebGL2の対応だけでは性能/容量は保証されない。実端末で落ちる場合は縮退または別実装を判断する。
- オフラインのPWAは保存消去リスクがある。実際に再起動・機内モードで確認し、利用者に準備済み状態を明示する。
- 汎用エンジン採用も自作もコストがある。比較スパイクの結果を見て決め、先に全面実装しない。

## 7. 議長の暫定結論・検証スパイク

第一試験はWebGL2の正則地形パッチ＋地理タイルキャッシュ＋CPU精密階層＋2D投影。既存Canvas2Dを比較基準として残す。Geometry Clipmaps、GPU raycast、汎用エンジンは必要に応じ比較。PC/Mobileで性能が満たせない場合は選定を再開する。描画のために解析の誤差要件を緩めない。

スパイクの順序（今回は計画のみ、実装開始の決定ではない）：
S1 同一の合成地形、境界、欠損、鋭い尾根、近景/遠景を既存CanvasとGPUパッチで比較。基準となるCPU first-hitと見える輪郭/距離を照合。32/64/128セル、複数画角、1/2px LODを比較。
S2 丹沢湖の既知の参考地点、近傍の移動、遠方の富士山、観測点より低い地表・山頂を含む複数シーン。同一DEM・高さ・座標・色設定を使用。参考地点は実写の確定地点とみなさない。地形データ提供元に配慮し、必要な範囲だけ取得。
S3 Mac M1のChrome/Safari、実機Android（機種未定）、入手可能ならiOS/Safari。デスクトップ1600x900、スマホ960x540の描画内部解像度から比較し、実際のDPR別にも記録。取得済み領域内の連続ピンドラッグ、10秒の方位パン、ズーム、視点高、時刻操作、複合操作を各3回。10分の連続操作で熱/劣化。別途冷起動と再訪、機内モード、タイル欠損、キャンセル、context lostを検証。
記録：p50/p95/p99フレーム間隔、表示される新規視点率、入力→最新視点の遅延、精密結果確定まで、アップロード量/回数、通信要求数/バイト、CPU/GPU管理メモリ、地形稜線誤差/欠損。フレーム間隔p95 16.7msを目標（60Hz、vsync揺らぎも記録）。稜線p95 0.05度は前回の改善目標。古いフレームの繰返しで60fps達成としない。目標を達成しない場合は負荷原因を特定しA/B/C比較へ進む。実測がないため速度・通信費・メモリの達成を主張しない。

次回は共通の地形・天体述語から、逆算探索の計算量削減、候補の漏れ/誤りの検証、広域探索とクライアントの限界を詳細化する。実装再開・公開時の製品範囲・商用配信方法は未決定。
